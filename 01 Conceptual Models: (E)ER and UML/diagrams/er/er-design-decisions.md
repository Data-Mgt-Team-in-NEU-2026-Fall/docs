# 校园二手交易平台 EER 图：关键设计决策

本文依据当前的 [EER 图](Seattle%20Campus%20Second%20Hand%20Market%20Place%20-%20EER%202.drawio) 整理概念模型。图中的实体与基数表示业务结构；下文标为“落地考量”的内容是实现时需要补充的约束，而非图中已经定义的字段或规则。

## 关键实体与业务链路

| 领域 | 关键实体 | 作用与关系 |
| --- | --- | --- |
| 身份与范围 | `USER`、`USER_ROLE`、`CAMPUS` | 用户属于一个校园，可有多个角色；买家与卖家是用户在交易中的不同角色，不是不同的用户子类型。 |
| 商品与发现 | `SECONDHAND_ITEM`、`ITEM_CATEGORY`、`ITEM_TAG` | 用户发布商品；每件商品归属一个分类，分类可形成父子层级；商品可关联多个标签。 |
| 交易 | `PURCHASE_REQUEST`、`TRANSACTION_ORDER`、`PICKUP_POINT` | 买家对指定商品提交请求；请求达成后最多产生一笔订单；每笔订单有买家、卖家和交接地点。 |
| 沟通与收藏 | `CONVERSATION`、`MESSAGE`、`SAVES` | 会话围绕一件商品展开并包含消息；用户可参与会话并发送消息；收藏是用户与商品之间带 `date_saved` 的关系。 |
| 反馈与治理 | `TRANSACTION_REVIEW`（`BUYER REVIEW`、`SELLER REVIEW`）、`REPORT`（`ITEM_REPORT`、`TRANSACTION_REPORT`） | 评价关联订单及评价双方；举报由用户提交，目标是商品或订单，两种子类型互斥。 |

主链路是“用户发布商品 → 买家就该商品提出购买请求 → 达成订单并约定交接地点 → 双方按交易身份评价”。收藏、会话和举报各自保留独立记录，不替代请求、订单或评价。

## 关键抉择与考量

1. **统一用户身份，分离权限与交易角色。** `USER` 与 `USER_ROLE` 是多对多关系，用户属于一个 `CAMPUS`；同一个人可以既买又卖，订单的 `BUYS` / `SELLS` 关系区分当次交易身份。这样无需复制用户资料，也便于按校园组织数据。落地考量：用户至少具备一个有效角色；订单买家与卖家应分别与对应请求的提交者、商品发布者一致，并防止自己向自己下单。
2. **将分类、标签和收藏分开。** 商品只归入一个分类，分类可有父分类；`ITEM_TAG` 提供多标签检索，`SAVES` 则是用户与商品的多对多关系，且自身保存 `date_saved`。三者分别承担导航、描述和个人收藏，不应混作商品上的文本或计数。落地考量：关系表应约束重复的用户-商品收藏和商品-标签组合；父子分类应避免循环。
3. **把出价、挂牌价与约定价放在不同阶段。** `SECONDHAND_ITEM.asking_price`、`PURCHASE_REQUEST.offered_price` 和 `TRANSACTION_ORDER.agreed_price` 分别记录标价、报价和双方约定价格；请求指向一件具体商品，一件商品可收到多条请求，但一条请求最多产生一笔订单。这样既保留协商历史，也不会因达成订单改写原挂牌信息。平台不处理线上付款；双方达成约定后形成订单并占用商品，其余请求设置为拒绝。线下交易后由卖家提交订单完成确认；订单买家或卖家均可取消订单，取消占用订单后重新开放新的购买请求，但不自动恢复已拒绝请求。落地考量：创建订单时核验请求、商品、买卖双方和状态，并防止并发形成多笔有效订单；图中尚未表达占用、拒绝、取消重新开放和卖家确认完成的规则。
4. **交接地点单独建模，订单必须指定地点。** `PICKUP_POINT` 保存地点名称、地址、坐标及启用状态，多个订单可复用同一地点；`pickup_datetime` 由订单保存。地点资料与交易约定分离，便于复用交接地点。落地考量：地点停用后如何处理已有订单，应保留历史约定而不是直接删除被引用的地点。

   卖家可保存自己的常用交接地点供后续订单选用；双方也可协商输入新地址，并将约定地址发送到会话。当前图尚未表达地点与卖家的归属及新地址的处理方式，因此不能将交接地点理解为全平台统一的必选地点。
5. **按商品组织会话，区分参与与发言。** 每个 `CONVERSATION` 讨论一件商品，用户参与会话，`MESSAGE` 分别归属会话并记录发送者、内容和时间。这样消息能还原到具体商品及发言人，而不是仅存买卖双方的自由文本。落地考量：发送者必须是会话参与者；图中会话至少有一条消息，若允许先建空会话，需调整创建流程或基数。
6. **评价按被评价的交易角色拆分。** `TRANSACTION_REVIEW` 保存评分、评论和状态，`BUYER REVIEW` / `SELLER REVIEW` 为互斥子类型；一笔订单每种评价最多一条，合计最多两条。这里“买家评价”指**评价买家**，而不是买家撰写的评价。落地考量：写入时校验作者和接收者是订单中的相对交易方，并明确哪些订单状态允许评价。
7. **举报目标互斥，交易举报限定参与者。** `REPORT` 统一记录原因、描述、时间和状态，`ITEM_REPORT` 与 `TRANSACTION_REPORT` 区分被举报商品和订单；一条举报只能指向两者之一。图中的业务规则还限定交易举报只能由对应订单的买家或卖家提交。落地考量：持久化时保证目标“恰有一个”，并在提交时校验举报人与订单的关系；处理状态不应覆盖原始举报内容。
