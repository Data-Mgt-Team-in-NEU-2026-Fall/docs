# 类图 1：用户身份与校园归属

对应图：[1.jpeg](1.jpeg)。

## 设计主体思路

以 `User` 为平台主体，将用户所属校园和用户角色独立建模。这样既能按校园组织用户，也能让同一个用户承担买家、卖家或管理员等不同职责，而不必为每种职责建立一套用户资料。

## 对应的用户用例

| 用例 | 类图覆盖内容 |
| --- | --- |
| `UC-1101` 使用校园邮箱登录 | `User`、`Campus` 和 `UserRole` 表达用户身份、校园归属与职责基础；邮箱登录和认证流程不在本类图中规定。 |
| `UC-1102` 查看个人交易记录 | `User` 是查询个人记录的主体；商品、请求、订单、收藏和评价分别由类图 2、4 描述，因此该用例需跨图汇总。 |
| `UC-1501` 举报商品或交易 | `User` 是举报人身份及权限判断的基础；举报目标、记录和处理流程见类图 4。 |

## 包含的实体

| 实体 | 作用 |
| --- | --- |
| `User` | 保存用户 ID、姓名、邮箱、电话、出生日期和加入时间；承担发布商品、收藏、提交购买请求和撰写评价等操作。 |
| `Campus` | 保存校园名称、地址及经纬度等位置资料。 |
| `UserRole` | 保存角色 ID 和角色名称，描述用户在平台上的权限或职责。 |

## 主要关系

- `User` **belongsTo** `Campus`：每个用户属于 1 个校园；一个校园可对应 0 到多个用户。
- `User` **hasRole** `UserRole`：每个用户有 1 到多个角色；一个角色可分配给 0 到多个用户。这是多对多关系。

## 特殊考量

- 角色与用户资料分离，避免用互斥的“买家/卖家”字段限制同一个用户同时买卖；权限仍须按角色核验。
- 图中要求用户至少有一个角色和一个校园。实现时应保证创建用户时这两种关联有效，而不是只保存名称文本。
- `Campus` 的地址和坐标用于定位及校园范围检索；用户的电话、出生日期属于个人信息，展示与访问应受到限制。
