# 类图 3：围绕商品的会话与消息

对应图：[3.jpeg](3.jpeg)。

## 设计主体思路

将沟通组织为针对具体商品的 `Conversation`，再将每条实际发送的内容记录为 `Message`。参与会话和发送消息是两种不同关系，便于保留完整的交流上下文。

## 对应的用户用例

| 用例 | 类图覆盖内容 |
| --- | --- |
| `UC-4301` 就商品沟通 | `Conversation` 关联具体商品及参与者，`Message` 记录会话内容和发送者，支持围绕商品的交流记录。 |
| `UC-4401` 达成订单和交接安排 | 会话与消息可承载双方协商及发送交接地址；订单与消息之间的直接关联未在本类图中表示。 |
| `UC-4402` 跟进线下交易 | 会话和消息保留历史交流；订单完成后停止发言、但允许查看历史的访问规则需由业务逻辑落实。 |

## 包含的实体

| 实体 | 作用 |
| --- | --- |
| `User` | 会话参与者和消息发送者。 |
| `SecondhandItem` | 会话讨论的商品，包含挂牌状态及商品描述等信息。 |
| `Conversation` | 记录会话 ID 和创建时间，并聚合参与者及消息。 |
| `Message` | 记录消息 ID、正文与发送时间。 |

## 主要关系

- 每个 `Conversation` 讨论 1 件 `SecondhandItem`；一件商品可对应 0 到多个会话。
- 每个会话有 1 到多名 `User` 参与；一个用户可参与 0 到多个会话。
- 每个会话包含 1 到多条 `Message`；每条消息归属 1 个会话。
- 每条消息由 1 名用户发送；一个用户可发送 0 到多条消息。

## 特殊考量

- 图中会话至少包含一条消息，若产品允许“先创建空会话再发送”，需明确创建时机或调整该基数约束。
- 发送者应是所属会话的参与者；仅凭消息上的用户关联不足以保证这一点。
- 会话与商品关联可以防止不同商品的沟通混杂；消息保留发送时间，以便按时间还原对话。
- 商品或用户状态发生变化时，历史消息是否保留、谁可查看以及能否继续发送，应由访问控制和保留策略明确。
